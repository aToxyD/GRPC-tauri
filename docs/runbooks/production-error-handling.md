# Runbook: التعامل مع أخطاء الإنتاج (Production Error Handling)

# الهدف
توضيح كيفية التعامل مع الأخطاء التي تحدث في بيئة الإنتاج، وكيفية استخراج تفاصيل الأخطاء الداخلية لغرض التصحيح دون المساس بالأمان أو خصوصية البيانات.

# النطاق
يطبق هذا الدليل من قبل مسؤولي النظام ومهندسي الدعم الفني. يعتمد هذا الدليل على سياسة ADR-0012 (عرض أخطاء الإنتاج).

# سياسة عرض الأخطاء
في نسخ الإنتاج (`--release`)، يعيد التطبيق رسائل خطأ عربية عامة فقط إلى واجهة المستخدم (Frontend). لا يتم إرسال التفاصيل الداخلية أبداً إلى الواجهة؛ بل يتم تسجيلها حصراً في "سجلات التطبيق" (Application Logs).

# خطوات التنفيذ

## 1. أين تظهر تفاصيل الأخطاء الداخلية؟
يتم تسجيل كافة الأخطاء الداخلية عبر `log::error!` بتنسيق محدد:
```text
[CommandError] code=INTERNAL | details=Some("Internal error: sqlite: no such table: products")
```

### التحكم في مخرجات السجل
يتم التحكم في مستوى التسجيل عبر متغير البيئة `RUST_LOG` قبل تشغيل التطبيق:
```powershell
$env:RUST_LOG = "error"          # تسجيل الأخطاء فقط (موصى به للإنتاج)
$env:RUST_LOG = "warn,grpc=info" # تسجيل الأخطاء + التحذيرات + معلومات grpc
```
في نظام Windows، تخرج السجلات إلى **stderr**. يمكن إعادة توجيهها إلى ملف:
```powershell
.\grpc.exe 2> C:\logs\grpc-errors.log
```

## 2. تنسيق سجل الخطأ
يحتوي السجل على الحقول التالية:
| الحقل | الوصف |
| :--- | :--- |
| `code` | كود الخطأ القابل للقراءة برمجياً (مثل `INTERNAL`, `DB_CONNECTION`). |
| `details` | الرسالة الداخلية الخام من Rust (آمنة للقراءة في السجلات، ويُحظر إرسالها للمستخدم). |

## 3. أكواد الأخطاء الشائعة والتشخيص

### `INTERNAL`
خطأ غير متوقع. التفاصيل تحتوي على سلسلة أخطاء Rust.
*   **الأسباب المحتملة**: خطأ في Migrations، عدم تطابق Schema، فشل Serialization، أو خطأ في IO.
*   **الإجراء**: قراءة `details` في السجل، التحقق من سلامة قاعدة البيانات عبر `PRAGMA integrity_check`.

### `DB_CONNECTION`
فشل في فتح قاعدة البيانات أو استنفاد تجمع الاتصالات (Connection Pool).
*   **الإجراء**: التأكد من وجود ملف القاعدة وعدم قفله من عملية أخرى، التحقق من حالة `PRAGMA wal_checkpoint`.

### `PARSE_DATE`
فشل في معالجة حقل التاريخ، غالباً بسبب بيانات مستوردة بتنسيق غير قياسي.
*   **الإجراء**: تحديد نص التاريخ في حقل `details` وتصحيح المصدر.

## 4. تصحيح الأخطاء دون كشف البيانات
لإعادة إنتاج مشكلة ما بشكل تفاعلي:
1.  شغل نسخة الإنتاج مع تفعيل `RUST_LOG=error` والتقاط stderr.
2.  قم بتنفيذ نفس الإجراء الذي أدى للخطأ.
3.  اقرأ السجل الملتقط للحصول على كامل التفاصيل.

**تحذير أمني**: لا تقم أبداً بنسخ محتوى `details` في إشعارات المستخدم أو رسائل البريد الإلكتروني.

## 5. تفعيل تفاصيل التصحيح الكاملة (للمطورين فقط)
لرؤية تفاصيل الخطأ مباشرة في الواجهة، يجب البناء في وضع **Debug**:
```powershell
cargo tauri dev
```
في بناء الـ Debug، يتم إلحاق `[dev: <details>]` برسالة الخطأ. **يُمنع منعاً باتاً** نشر بناء Debug في بيئة الإنتاج.

# التحقق والتدقيق
عند إبلاغ مستخدم عن خطأ:
*   [ ] الحصول على نص رسالة الخطأ التي ظهرت للمستخدم.
*   [ ] مطابقتها مع السجل باستخدام الطابع الزمني.
*   [ ] قراءة `details` من السجل لتحديد السبب الجذري.
*   [ ] إذا تعذر الحل، يتم التصعيد بإرفاق سجل الخطأ الداخلي (وليس النص الظاهر للمستخدم).
