# Runbook: تركيب وتفعيل التراخيص (Licensing Installation)

# الهدف
توثيق عملية تركيب مرساة الثقة (Trust Anchor) والترخيص الموقّع على عقدة GRPC، والتحقق من
تفعيل بوابة التراخيص، وفق السلوك المثبت عبر إشهاد A2 (2026-08-09) على ثنائي Release.

# النطاق
- تثبيت anchor وترخيص واحد أو أكثر.
- التحقق من الحالة (`VALID` / نشط).
- فهم خريطة الصلاحيات (Entitlements) وسلوك البوابة.
- التجديد والإلغاء وتدوير anchor.

# مراجع
- `docs/architecture/0042-licensing-consumer-integration.md` — قرار الاستهلاك (Consumer-only).
- `docs/architecture/0041-production-app-key-provisioning.md` — توفير مفتاح التطبيق.
- `docs/runbooks/licensing-node-binding.md` — سلوك ربط الترخيص بالعقدة.
- `docs/runbooks/key-loss-and-reprovisioning.md` — فقدان المفاتيح وإعادة التزويد.

# المفاهيم الأساسية
- GRPC **مستهلك** فقط: يستورد، يتحقق، يربط، ويفرض الصلاحيات — ولا يصدر التراخيص ولا يعدّلها.
- الرأي المحلي للترخيص هو **عرض مشتق قابل للاستبدال** (Derived View) مخزّن في
  جداول `licensing_anchor` / `licensing_license` / `licensing_events`.
- التحقق محلي وحتمي تماماً (بدون شبكة، بدون ساعة حائط): البنية → الإصدار → الهوية →
  التوقيع → **ربط العقدة** → الدلالة → الفرض.
- الترخيص مرتبط بمفتاح العقدة: التوقيع الصحيح وحده لا يجعل الترخيص صالحاً لهذه العقدة
  (راجع `licensing-node-binding.md`).

# المتطلبات المسبقة
- هوية عقدة نشطة (يوجد مفتاح عقدة — إقلاع الهوية مكتمل).
- جلسة مصادقة نشطة بصلاحية `ManageLicensing` (إدارة التراخيص) أو `ReadLicensingStatus` (قراءة فقط).
- حل `GRPC_ROOT_PUBLIC_KEY` عند الحاجة للتحقق من شهادات الهوية (مستقل عن التحقق من الترخيص).

# واجهة الأوامر (IPC)
الأوامر التالية مثبتة عبر إشهاد A2 (عبر IPC مباشر):

| الأمر | الوظيفة | ملاحظة |
|---|---|---|
| `get_licensing_status` | عرض anchor + التراخيص + ملخص البوابة | `{ anchor, licenses, summary }` |
| `import_trust_anchor` | تثبيت/استبدال anchor النشط الوحيد | حزمة `provisioning-v1` |
| `import_license` | تحقق كامل + تخزين العرض المشتق | نتائج `imported` / `rejected` / `not-for-this-node` |
| `dry_run_verify_license` | تحقق كامل دون تخزين (معاينة) | لا يغيّر الحالة |
| `verify_license` | إعادة تحقق حتمية من التخزين | `{ checked, enforceable, results }` |

> **اصطلاح أسماء الوسائط (مثبت من A2)**: أسماء وسائط الأوامر على مستوى Tauri تُمرَّر
> **camelCase** — مثل `packageJson` و`artifactJson` (وليس `package_json` / `artifact_json`).

# خطوات التركيب

## 1. التحقق من الحالة الحالية
```text
get_licensing_status
```
- `summary.anchor_installed` — هل يوجد anchor نشط؟
- `summary.license_count` — عدد التراخيص المخزنة.
- `summary.gate_active` — البوابة خاملة حتى يُثبَّت anchor نشط (ADR-0042 §5).

## 2. تثبيت مرساة الثقة
```text
import_trust_anchor { packageJson: "<حزمة provisioning-v1>" }
```
- الشكل: `{ format: "provisioning-v1", key_id, algorithm: "Ed25519", public_key }`.
- يُثبَّت **anchor نشط واحد فقط**؛ استيراد حزمة أحدث **يستبدل** anchor الحالي (تدوير) ويعيد
  `replaced_key_id`، والاستيراد المتزامن لثانٍ مرفوض.
- لا يوجد anchor → أي artifact معروض يُرفض (Fail-Closed).

## 3. استيراد الترخيص
```text
import_license { artifactJson: "<artifact موقّع>" }
```
- النتيجة `outcome = "imported"` تعني التحقق الكامل وربط العقدة والتخزين.
- الـartifact لنفس `license_id` يستبدل العرض المشتق كاملاً (وليس دمجاً).
- إعادة استيراد نفس الـartifact هي عملية Idempotent (نفس `artifact_id`).

## 4. التحقق النهائي
```text
verify_license
```
- `checked` = عدد التراخيص المفحوصة، `enforceable` = عدد التراخيص القابلة للفرض
  (نشطة + تعيد التحقق صحيحاً + مرتبطة بهذه العقدة).
- الترخيص قابل للفرض فقط إذا كان **نشطاً** ويعيد التحقق (المسار الكامل) و**مطابقاً للعقدة الحالية**.

# خريطة الصلاحيات (Entitlements)
الصلاحيات معلنة **داخل الحمولة الموقّعة** ولا تُستنتج محلياً. الخريطة الثابتة الوحيدة
(من `docs/architecture/0042-licensing-consumer-integration.md` §5):

| مفتاح الصلاحية | مجموعة الميزات المُفرَضة في GRPC |
|---|---|
| `core.auth` | مصادقة / وصول الهوية |
| `core.sync` | استيراد/تصدير حزم المزامنة |
| `core.reports` | التقارير اليومية/الشهرية/الولايات |
| `core.stock` | المخزون، حركات المخزون، المنتجات |
| `core.consume` | الطلبات / عمليات الاستهلاك |
| `core.admin` | الإجراءات الإدارية والحوكمة |

> مثال مثبت (A2): `create_product` يقع ضمن `core.stock` — ترخيص بصلاحية `core.stock` يسمح به،
> وترخيص بصلاحية أخرى لا يمنحه.

- مفتاح صلاحية **غير موجود في الجدول** → يُرفض عند الاستيراد (Fail-Closed).
- بدون ترخيص قابل للفرض، تبقى العقدة محصورة في **المجموعة المعفاة** (انظر أدناه)، وكل
  العمليات الأخرى مرفوضة (Fail-Closed افتراضياً).

# المجموعة المعفاة (Exempt)
الأفعال التالية لا تتطلب ترخيصاً (تظل متاحة حتى للعقدة غير المرخّصة): إدارة التراخيص وقراءة
حالتها، الإعداد الأمني وإدارة مفتاح التطبيق، تزويد الهوية/المزامنة/التدوير، الصحة النظامية
وقراءة سجل التدقيق والنسخ الاحتياطي، وأفعال التمهيد (`ConfigureAsWilaya` / `AdminOnly` /
`AuthenticatedOnly`). كل ما عدا ذلك محجوب عند غياب الترخيص.

# مرجع النتائج والرسائل (مثبتة من A2)

| الحالة | النتيجة | الرسالة |
|---|---|---|
| استيراد ناجح ومرتبط بالعقدة | `outcome = "imported"` | `license imported` |
| توقيع صالح لكنه مرتبط بعقدة أخرى | `outcome = "not-for-this-node"` | `license is not bound to this node` |
| فشل التحقق / دلالة غير معروفة / لا anchor | `outcome = "rejected"` | رسالة السبب |

رسائل الرفض الصادرة عن بوابة التفويض (عبر `authorize_command`):
- لا يوجد ترخيص قابل للفرض: `غير مرخّص: لا يوجد ترخيص سارٍ لهذه العملية`.
- ترخيص صالح لكن ينقصه مفتاح الصلاحية المطلوبة: `غير مرخّص: الترخيص لا يمنح الصلاحية المطلوبة (core.<key>)`.

> ملاحظة: على نتيجة `not-for-this-node`، يعيد الأمر `license_id` و`artifact_id` لتحديد الـartifact
> الذي قُيّم (مثبت من A2) — لكن لا يُخزَّن أي شيء على العقدة وتبقى غير مرخّصة.

# التجديد والإلغاء
- التجديد/الإلغاء يُسلَّمان كـartifact موقّع جديد: مع `status: "revoked"` يتوقف الفرض على
  الصلاحيات الممنوحة سابقاً. لا يوجد أمر "إلغاء" محلي.
- الاستيراد يستبدل العرض المشتق لـ `license_id` المقابل كاملاً.

# تدوير المرساة
استيراد حزمة `provisioning-v1` جديدة يستبدل anchor النشط الوحيد (مع `replaced_key_id`).
لا تُحتفظ مراسٍ متزامنة متعددة.

# ملاحظة: مسار الواجهة الرسومية (Finding A3-1)
> **حالة غير معتمدة**: مسار استيراد anchor/license من صفحة الواجهة (`LicensingPage`) غير
> معتمد كمسار عمل حالي. إشهاد A2 كشف أن طبقة العقد في الواجهة
> (`src/lib/contracts/licensing.contract.ts`) ترسل أسماء وسائط snake_case
> (`package_json` / `artifact_json`) بينما يتطلب الـIPC الفعلي camelCase
> (`packageJson` / `artifactJson`)، ما يجعل الاستيراد من الواجهة يفشل برسالة
> `missing required key`. **المسار المثبت والعامل هو استيراد الـartifact عبر IPC مباشر**
> (كما في هذا الدليل). يُسجَّل هذا كخلل كودي (implementation defect) خارج ADR-0042،
> ويُرجأ إصلاحه إلى ما بعد A3.
