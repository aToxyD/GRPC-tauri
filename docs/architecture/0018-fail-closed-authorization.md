# ADR 0018: سياسة التفويض وفق مبدأ التوقف الآمن (Fail-Closed Authorization)

# الحالة
مقبول

# السياق
خلال مراجعة التدقيق الأمني (Final Adversarial Re-audit)، تم اكتشاف وجود ثغرات في موجّهات سياسة التفويض (`authorize_reports` و `authorize`) تتمثل في استخدام المطابقات العامة (`_ => Ok(())`). هذا النمط المعروف بـ "Fail-open" يعني أن أي إجراء (Action) جديد يتم إضافته للنظام، أو أي إجراء يتم توجيهه بشكل خاطئ، سيتم منحه الوصول افتراضياً، مما ينتهك مبدأ الحد الأدنى من الصلاحيات (Principle of Least Privilege).

# القرار
تم إعادة هيكلة معمارية التفويض لتصبح "Fail-closed" بشكل صارم:

1.  **المطابقة الشاملة (Exhaustive Matching):** يجب أن تقوم دالة التوجيه `authorize` وكافة السياسات الفرعية بمطابقة كل تنوعات الـ `Action` enum بشكل صريح.
2.  **الرفض الافتراضي (Default Deny):** يجب أن يعيد الذراع العام (`_ =>`) في أي سياسة فرعية خطأ `Err(AuthorizationError::InsufficientPermissions)`.
3.  **القواعد الصريحة:** يجب أن يقوم كل إجراء محدد في السياسة بالتحقق صراحة من دور المستخدم (`Principal::role`) وسياق المورد (`ResourceContext`). لا يُسمح بأي استثناءات ضمنية.
4.  **حارس المصادقة (Authenticated Guard):** يتم توجيه إجراءات النطاق العامة (مثل `ReadProducts`) إلى `authorize_authenticated()`، مما يوفر ضمانة برمجية وقت التجميع (Compile-time) بأن الإجراء قد تمت دراسته صراحة، حتى لو كان المتطلب الوحيد هو وجود جلسة صالحة.

# النتائج المترتبة
*   **الأمن:** فرض معمارية "انعدام الثقة" (Zero-trust). إضافة أي أمر أو إجراء جديد تتطلب قراراً واعياً وصريحاً بشأن سياسته الأمنية؛ وإلا فسيتم رفض الإجراء تلقائياً.
*   **الصيانة:** يفرض مترجم Rust (Compiler) الشمولية في مطابقة الـ `Action` العلوي، مما يضمن عدم نسيان تأمين أي نوع إجراء جديد من قبل المطورين.
