# ADR 0017: الاستعادة الآمنة والذرية والتعافي من الانهيار (Atomic Secure Restore)

# الحالة
مقبول

# السياق
كان التنفيذ السابق لعملية `restore_backup_atomic` يحتوي على ثغرة أمنية حرجة؛ حيث كان يقوم بفك تشفير كامل قاعدة بيانات SQLite في الذاكرة العشوائية (RAM)، ثم كتابتها في مسار معروف على القرص قبل التحقق منها. كان هذا يعرض بيانات القاعدة الصريحة للتسرب على القرص، ويخاطر بترك ملفات صريحة يتيمة في حال انهيار النظام أثناء العملية.

# القرار
يجب ضمان ذرية (Atomicity) عملية استعادة قاعدة البيانات من خلال مراحل إعداد آمنة ومنطق صارم للتعافي من الانهيار:

1.  **الإعداد الآمن (Secure Staging)**: يتم بث عملية فك التشفير مباشرة إلى ملف مؤقت باسم عشوائي (`*.sqlite_tmp`) يقع في نفس دليل قاعدة البيانات المستهدفة. يتم إنشاء الملف بصلاحيات مقيدة جداً (0600) ويحذف تلقائياً في حال فشل العملية.
2.  **عدم استخدام ذاكرة كاملة**: تستخدم عملية فك التشفير تقنيات البث المبطن؛ بحيث لا يتم تخزين قاعدة البيانات الصريحة بالكامل في الذاكرة أبداً.
3.  **التحقق الموقعي (In-Place Validation)**: يتم تشغيل `PRAGMA quick_check` مباشرة على الملف المؤقت قبل اعتماده.
4.  **سجل التعافي من الانهيار (Crash-Recovery Journal)**: بمجرد التحقق، يتم كتابة سجل صغير بصيغة JSON (`restore.journal`) بشكل ذري. يسجل هذا الملف مسار الملف المرشح ومسار التراجع (Rollback).
5.  **التعافي عند بدء التشغيل**: عند بدء تشغيل التطبيق، تقوم دالة `recover_interrupted_restore_and_orphans` بفحص السجل وإتمام أي عمليات استبدال (Swap) غير مكتملة، مع الحذف الآمن لأي ملفات مؤقتة يتيمة.

# النتائج المترتبة
*   **إعداد آمن**: لا يتم كتابة قاعدة البيانات الصريحة أبداً في مسار دائم أو معروف قبل اجتياز فحوصات السلامة.
*   **سلامة عند الانهيار**: في حال انقطاع الطاقة أو انهيار التطبيق، يضمن السجل (Journal) استئناف العملية بأمان عند إعادة التشغيل، مما يمنع تلف القاعدة أو ترك بيانات حساسة يتيمة.
*   **الأداء**: تقليل ذروة استهلاك الذاكرة بشكل كبير أثناء الاستعادة من خلال تجنب التخزين المؤقت للملف بالكامل.
