# التوثيق التقني لنظام GRPC-tauri

# الهدف
هذا المستند موجه للمطورين والمحافظين على النظام (Maintainers). يهدف لتوفير حقائق هندسية مجردة، توضيح القيود التشغيلية، وترسيخ القواعد المعمارية الصارمة للنظام، بعيداً عن المصطلحات التسويقية.

# النطاق
يغطي هذا التوثيق المعمارية البرمجية، النموذج الأمني، استراتيجيات معالجة البيانات، والضمانات الحتمية (Deterministic) لإدارة السنة المالية والنسخ الاحتياطي.

# 1. الفلسفة المعمارية
يعتمد النظام على نمط **Monolith** منظم وفق المعمارية الطبقية (Layered Architecture).

## قواعد الصيانة المعمارية (Maintenance Rules)
1.  **Thin Commands**: يجب أن تقتصر مسؤولية أوامر Tauri على استقبال الطلبات وتوجيهها فقط.
2.  **Unified Authorization**: كافة عمليات التفويض (Authorization) تمر حتماً عبر `application::authz`.
3.  **Unified Import Pipeline**: أي عملية استيراد بيانات خارجية يجب أن تخضع للمسار الموحد `run_import_pipeline`.
4.  **No Direct DB in Guards**: يُمنع إجراء استعلامات مباشرة لقاعدة البيانات داخل حراس الأوامر (Guards).
5.  **No String Role Checks**: يتم التحقق من الصلاحيات عبر الـ Context والـ Actions وليس بمقارنة نصوص الأدوار.
6.  **No read_to_end**: يُمنع استخدام `read_to_end` للملفات الكبيرة؛ يجب استخدام **Buffered IO**.
7.  **Exclusive age::x25519**: لا يُسمح باستخدام `age::scrypt` أو أي خوارزميات تشفير قديمة.
8.  **Session Integrity**: العمليات الطويلة يجب أن تستدعي `touch_session()` لضمان استمرار الجلسة.
9.  **Infrastructure Isolation**: طبقة الـ Domain يجب أن تظل مستقلة عن طبقة الـ Infrastructure.
10. **Application Orchestration**: تنسق طبقة التطبيق العمليات، بينما تتخذ طبقة الـ Domain القرارات المنطقية.

# 2. النموذج الأمني (Security Model)

## التشفير
*   يستخدم النظام `age::x25519` حصراً لتشفير النسخ الاحتياطية (Backups) وحزم المزامنة (Sync Packages).
*   **GRPC_APP_KEY**: هو الهوية التشفيرية (Identity) لـ `age`. فقدان هذا المفتاح يعني استحالة استعادة البيانات.
*   لا تُدرج أي "مفاتيح تطوير" في بناءات الإنتاج (Release builds).

## السلامة (Integrity)
*   يتم التحقق من HMAC إجبارياً لكل حزمة (Package) يتم استيرادها.
*   يستخدم النظام `SHA-256` لضمان سلامة سلسلة التدقيق (Audit Chain).

## حدود الحماية
*   يحمي النظام من التلاعب بالبيانات "أثناء السكون" أو "أثناء النقل" (Offline Packages).
*   **لا** يحمي النظام من مستخدم يمتلك صلاحيات كاملة على نظام التشغيل (Root/Admin) أو الوصول المباشر للذاكرة الحية.

# 3. معالجة البيانات والأداء

## إدارة الذاكرة (Memory Management)
*   يتم استخدام **Buffered IO** في كافة عمليات القراءة والكتابة.
*   **تنبيه**: حمولات JSON يتم تحويلها بالكامل في الذاكرة (Materialized) قبل المعالجة؛ لذا يتناسب استهلاك الذاكرة طردياً مع حجم البيانات المستوردة.

## الأداء و SQLite
*   يعمل SQLite بوضع **WAL** (Write-Ahead Logging) لتحسين التزامن.
*   النظام مخصص للاستخدام المحلي/الفردي؛ ولا يدعي القدرة على التوسع اللانهائي (Scalability).

## الضمانات الحتمية
*   **UTC**: تُستخدم توقيتات UTC حصراً في أسماء الملفات والطوابع الزمنية لتجنب تضارب المناطق الزمنية.
*   **سلسلة التدقيق**: يفرض التحقق `verify_chain_stream` ربطاً صارماً بين السجلات عبر الـ Hash، مما يكشف أي محاولة لإعادة ترتيب أو حقن سجلات مزورة.
*   **الاستعادة بعد التعطل**: يقوم النظام تلقائياً بمعالجة عمليات الـ Swap الذرية غير المكتملة وتنظيف الملفات المؤقتة اليتيمة عند إعادة التشغيل.

# 4. مسار الاستيراد الموحد (Canonical Import Flow)
أي أمر استيراد يجب أن يتبع هذا التسلسل:
1.  **Command Receive**: استلام البيانات أو المسار.
2.  **Authorize**: التحقق من تفويض المشغل.
3.  **Touch Session**: تحديث صلاحية الجلسة.
4.  **Audit Start**: تسجيل بداية العملية.
5.  **Run Import Pipeline**:
    *   فتح Transaction في قاعدة البيانات.
    *   التحقق من HMAC وسلامة البيانات (Integrity).
    *   المعالجة عبر الـ Import Service.
6.  **Audit Success/Reject**: تسجيل النتيجة النهائية وإتمام الـ Transaction (Commit/Rollback).

# 5. إدارة السنة المالية (Fiscal Management Hardening)
*   تحديث `settings.current_year` يتم بشكل ذري (Atomic) ضمن نفس الـ Transaction الخاص بالإغلاق.
*   يفشل تشغيل التطبيق فوراً إذا اكتشف تعارضاً بين السنة المالية المفتوحة والإعدادات المسجلة.
*   يتم حساب أرصدة الافتتاح وتوثيقها في سجل التدقيق مع الـ Snapshot الإجمالي للمخزون.

# 6. حدود التشغيل وسلامة المشغل (Operational Trust)

## حدود العمليات (Transaction Boundaries)
*   عمليات `close_year`, `archive_year`, و `record_export_snapshot` يجب أن تنفذ داخل `db.with_transaction`.
*   أي فشل في تسجيل التدقيق أو تحديث الإعدادات يؤدي لعملية Rollback كاملة.

## السنوات المالية المؤرشفة
*   يمنع `FiscalHistoricalGuard` أي تعديل أو استعادة (Restore) تستهدف سنوات مؤرشفة لضمان عدم المساس بالسجلات التاريخية.

## رموز التنفيذ (Execution Tokens)
*   يتم توليد رموز تنفيذ مؤقتة `SHA256(operation|state_fingerprint)` للعمليات الحساسة.
*   يصبح الرمز غير صالح (`STALE_EXECUTION_TOKEN`) فور تغير حالة قاعدة البيانات.
*   يتم خنق العمليات المتكررة (`OPERATION_THROTTLED`) لمنع التنفيذ المزدوج غير المقصود.

# 7. دورة حياة التحقق من النسخ الاحتياطية (Fail-Closed)
يطبق النظام مسار تحقق متعدد المراحل لمنع التلف الصامت:

1.  **WAL Checkpoint Verification**: تنفيذ `PRAGMA wal_checkpoint(TRUNCATE)` والتأكد من تصفير كافة الإطارات (Frames).
2.  **SQLite Backup API**: استخدام الواجهة الرسمية لـ SQLite لإنشاء لقطة (Snapshot) متسقة زمنياً.
3.  **Pre-Encryption Validation**:
    *   التحقق من وجود الملف وحجمه المنطقي.
    *   تنفيذ `PRAGMA integrity_check` على الملف المؤقت قبل تشفيره.
    *   مقارنة عدد الصفحات (Page Count) وحجم الصفحات (Page Size) مع المصدر.
4.  **Encryption & Persistence**: التشفير المتدفق (Streaming) عبر `age` مباشرة إلى المخرج النهائي.
5.  **Audit Trail**: تسجيل كافة قياسات التحقق ونتائج الفشل أو النجاح في سجل التدقيق.

**ضمانات Fail-Closed**:
*   لا يتم إنشاء نسخة احتياطية في حال فشل الـ Checkpoint.
*   لا يتم تشفير أو حفظ أي نسخة تفشل في اختبار السلامة (Integrity Check).
*   يتم الحذف الآمن للملفات المؤقتة فور الفشل أو اكتمال التشفير.

# 8. القيود التشغيلية (Operational Limits)
*   **البيئة**: تطبيق سطح مكتب أوفلاين.
*   **قاعدة البيانات**: الحجم الموصى به < 500MB لضمان كفاءة العمليات.
*   **حزمة المزامنة**: الحد الأقصى 512MB.
*   **سجل التدقيق**: التصدير محدد بـ 50,000 سطر لضمان استقرار واجهة المستخدم (UI).

# 9. بيئة التشغيل والتحكم في النسخ (Runtime & Instance Control)
*   **Single Instance Enforcement**: يمنع النظام تشغيل أكثر من عملية (Process) واحدة في نفس الوقت لضمان اتساق الوصول إلى ملفات SQLite وتجنب تضارب الجلسات.
*   **IPC Detection**: عند تشغيل نسخة ثانية، يتم إرسال إشارة للنسخة الأصلية لتركيز النافذة (Focus) وإظهار تنبيه للمستخدم، ثم تنتهي العملية الجديدة فوراً.
*   **Fail-Closed Startup**: إذا فشلت آلية التحقق من وجود نسخة سابقة (Startup Lock)، يمنع التطبيق التشغيل لضمان عدم خرق سلامة البيانات.

# 10. الصيانة والتدقيق المعماري
يجب تشغيل `check:arch` دورياً لضمان الالتزام بالقيود البرمجية. أي خرق للسلامة البنيوية يتطلب تدخل المسؤول واستعادة النظام لحالة مستقرة.
