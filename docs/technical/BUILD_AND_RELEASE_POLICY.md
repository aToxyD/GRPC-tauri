# سياسة بناء وإصدار النظام (Build & Release Policy)

تحدد هذه السياسة المعايير والإجراءات اللازمة لضمان سلامة حزم الإصدار وقابلية تكرار عملية البناء (Reproducibility).

# 1. بناء الإصدارات الحتمية (Deterministic Release Builds)
*   **البيئة**: يجب استخدام بيئة بناء معزولة ومستقرة (مثل GitHub Actions أو CI/CD محلي).
*   **المميزات (Features)**: يجب تفعيل ميزة `custom-protocol` وتعطيل أي ميزات تجريبية.
*   **الملف الشخصي (Release Profile)**:
    *   `lto = true` (Link Time Optimization)
    *   `codegen-units = 1`
    *   `panic = 'abort'` (لتقليل حجم الملف وضمان سلوك Fail-Fast)
    *   `strip = true` (إزالة رموز التصحيح في نسخة الإنتاج)

# 2. بصمة الإصدار (Version Fingerprint)
يحتوي كل بناء على "بصمة" تتضمن:
*   **إصدار التطبيق**: المذكور في `Cargo.toml`.
*   **إصدار المخطط (Schema Version)**: لضمان توافق قاعدة البيانات.
*   **وقت البناء (Build Timestamp)**: وقت إنشاء الحزمة.
*   **معرف الالتزام (Git Commit Hash)**: إذا كان متاحاً.

# 3. سياسة التوقيع (Signing Policy)
*   يجب توقيع كافة الملفات التنفيذية لنظام Windows بشهادة صالحة لتجنب تحذيرات SmartScreen.
*   يتم التحقق من توقيع التطبيق عند التشغيل الأول في بيئات الإنتاج الحساسة.

# 4. إدارة التغييرات الجذرية (Breaking Changes)
*   أي تغيير في `SchemaVersion` يعتبر تغييراً جذرياً يتطلب خطة هجرة (Migration Plan).
*   أي تغيير في بروتوكول المزامنة يفرض رفع إصدار البروتوكول ورفض الحزم القديمة فوراً.

# 5. سياسة التراجع (Rollback Policy)
*   لا يدعم النظام التراجع التلقائي (Auto-rollback) لقاعدة البيانات بعد الهجرة.
*   يجب أخذ نسخة احتياطية كاملة قبل تثبيت أي إصدار جديد.
*   عند حدوث فشل حرج، يتم استعادة النسخة الاحتياطية وإعادة تثبيت الإصدار السابق.

# 6. تسمية الملفات (Naming Convention)
*   قالب التسمية: `GRPC_v[Version]_[Platform]_[BuildDate].exe`
*   مثال: `GRPC_v1.0.0_windows_2026-05-16.exe`

# 7. التحقق من سلامة البناء (Build Integrity Verification)
بعد البناء، يتم توليد ملف `SHA256SUMS` يحتوي على بصمات كافة المخرجات. يجب على المشغل التحقق من البصمة قبل التوزيع.
